# Procedural city engine

> Retired production path (2026-10-26): the owner rejected this city-first implementation. Its runtime generator, contracts, network/district/parcel orchestration and city CLI commands are removed. The content below is historical evidence, not current API instructions. Follow the [world master plan](ADVANCED_WORLD_GENERATION_MASTER_PLAN.md) and [active tracker](ROADMAP.md) for the replacement. No compatibility/legacy generator is retained.

## Reusable standalone grounds (2026-10-26)

`SiteAreaDefinition` adds reusable ground/activity surfaces to provider and content `Areas` inventories. Definitions contain ID, arbitrary game-authored kind/purpose, exact `SiteAreaSizeVariant` widths/depths/clearance, an explicit `AllowsThroughAccess` boolean, optional access/minimum-road widths and custom properties. No height, building capacity, settlement demand, equipment identity or artwork is invented. `list-areas <catalog-id> [kind]` lists their definitions/variants separately from buildings and objects. `ReplaceAreaIds` and positive `CatalogImport.AreaIds`/`AreaOrigins` preserve source ownership and one current definition per ID.

`FacilityProgramPart.Kind=GroundArea` selects a definition and exact variant. The existing frontage grammar computes a separate `FacilityAreaSlot` reserved site; `SiteAreaPlanner` uses shared physical fitting to place the unscaled surface and optional approach. Mixed, repeated, nested and ground-only programs/providers use the same facility compiler. Source slots, components, custom properties, through-access and road requirements are validated/snapshotted. Unknown/missing variants, infeasible sizes, overlaps, disconnected roads and exceeded budgets fail explicitly. Zero access width creates no approach/link. Through-access is an explicit game rule, independent of the kind name; these are geometry constraints, not native navigation or simulation.

There is one `PlannedSiteArea` output collection for building/compound bands and standalone grounds. Its current `Kind` is a string; the enum-only output contract is replaced without aliases/converters. `Band` is nullable for standalone areas. New fields retain `AllowsThroughAccess`, `ReservedSite`, `SourceKey`, `Access`, width/road and components. Existing typed building-site rules retain their current semantics; their generated areas now state the same traversal policy explicitly. `AreaDefinitions` on city/metadata documents stores resolved source/variant facts, separately from building and object facts. Standalone grounds consume `MaximumSiteAreas`, not structure/object inventory.

The city preserves the surface, reserved site, ownership and approaches through arbitrary road-aligned rotations. Metadata uses an owned `area-site` plus a `site-area` surface, optional typed `area-access`, exact polygons/widths, source key/components and actual polygon orientation. The Metadata disclosure shows the resolved area definition and variant. Source facts and geometry are rebuilt during validation/package verification; missing/forged surfaces, owners, policies, components, approaches and facts reject.

Non-through areas remain clear of full native road/access sweeps, including bevel joins, and all grounds remain clear of physical structures/equipment. This exposed a prior nested-route defect: inline compound lanes used a fixed four-meter gap despite a member declaring six-meter access. Shared lanes, padding and entry reservations now use resolved member widths, through the same grammar and validator. Source physical dimensions remain unchanged; an infeasible compound is rejected instead of fitting paths through protected land or searching vacant points.

[Reusable inputs](../examples/procedural-city/catalog-areas/) include aligned/rotated requests and shared source content. Current matching-build packets: `generated/procedural-city/catalog-areas-v2` and `generated/procedural-city/catalog-areas-rotated-v2`. Each has four standalone grounds from three definitions/four available variants, 22 total site areas, four equipment objects, nine internal roads, 38 solid perimeter pieces and 16 openings. These examples demonstrate current rectangular frontage slots/surfaces and nested ownership, without certifying whole-city design, detailed terrain, simulation, art or runtime. [Current evidence](SDLC_VERIFICATION.md#standalone-catalog-grounds-2026-10-26).

## Catalog equipment and site objects (2026-10-26)

Reusable `SiteObjectDefinition` records live in `ISettlementCatalogProvider.Objects` and `CatalogContentManifest.Objects`. A definition supplies an arbitrary game-authored `Id`, `Kind`, `Purpose`, physical `Variants`, `BlocksMovement`, optional `AccessWidthMeters`/`MinimumRoadWidthMeters` and custom JSON `Properties`. A `SiteObjectSizeVariant` supplies ID, width/depth/height and clearance in meters. Width/depth must be positive; zero-height nonblocking markers are supported. Definitions have no invented building capacity, settlement demand or resource profile. `list-objects <catalog-id> [kind]` lists object/variant counts separately from `list-buildings`. Modern's existing building inventory does not turn into equipment; game-authored content adds reusable objects explicitly.

`FacilityProgramPart.Kind=Equipment` resolves an exact object definition/variant and compiles a separate `FacilityObjectSlot`. The current frontage grammar calculates its reserved site from the source dimensions, setbacks and clearance. `SiteObjectPlanner` shares the physical-envelope solver with buildings, preserves the selected physical size and rejects infeasible fitting. Components remain declared metadata, without generated animation/artwork. Mixed buildings/objects, nested object-only yards and independent object-only providers/composed catalogs use the same `FacilityCompositionPlanner.PlanGeometry`. Slot ownership, explicit imports (`CatalogImport.ObjectIds`), source digests and replacement IDs remain mandatory. Object definitions/properties are immutable snapshots; custom property ordering is stable across processes.

Objects with zero access width have no invented route or connection. Declared positive widths produce an exact access polygon/centerline and require the authored frontage road to meet the declared width. Blocking objects remain clear of physical buildings, road/access sweeps and solid site boundaries. Nonblocking is an explicit game rule, not an inferred object category. No site is relocated or scaled to fix a conflict. The neutral facility planner also checks full building/object access widths against solids. Source templates keep their existing rectangular frontage grammar; the city transforms the complete plan at the actual road-aligned rotation.

`ProceduralCityDocument.Objects` contains separate physical placements, reserved sites, root/group ownership, source key, kind/purpose, height, movement flag, access width/road, rotation and component metadata. `ObjectDefinitions` contains exact resolved source facts; objects never enter `Structures` or `SourceStructures`. City validation rebuilds these facts and geometry and rejects missing/extra/forged objects, owners, components, dimensions or source definitions. `MaximumObjects` defaults to 5,000; facility/member, package and schematic budgets still apply.

Metadata exports owned `object-site` and physical arbitrary-kind nodes, typed `object-access` connections only when declared, exact polygons and road widths, and separate `ObjectDefinitions`. The physical node has no `StructureKey`. The schematic's Metadata disclosure shows the resolved source/variant/custom properties. File generation, catalog saving/listing, failures and package verification use the existing reporting/audit boundary.

[Reusable inputs](../examples/procedural-city/site-objects/) include aligned and rotated requests plus source content. Matching-build packets are `generated/procedural-city/site-objects` and `generated/procedural-city/site-objects-rotated`. Each has four object instances from three definitions/four available variants, alongside nested buildings, 18 surrounding areas, eight internal roads, 32 solid perimeter pieces and 14 openings. This demonstrates the mechanism, not a universal equipment inventory or accepted city design. [Current evidence](SDLC_VERIFICATION.md#catalog-site-objects-2026-10-26) covers API/CLI, exact geometry and browser/export checks. Interiors, arbitrary terrain/attachment/surface grammars, simulation, production artwork and native runtime remain separate work.

## Site perimeters and openings (2026-10-26)

`SiteBoundaryRule` declares `Id`, game-authored `Kind`, `Purpose`, `ThicknessMeters`, `HeightMeters`, `MinimumOpeningMeters` (default 2) and `OpeningClearanceMeters` (default 0.25). Rules are optional. Author them on a compound `CityStructureType`, an included-surroundings `BuildingDefinition`, or a reusable `FacilityProgramDefinition`/`FacilityDefinition`. Registered rules reach their actual generated site/group; source physical-only references keep their explicit physical-only behavior. Supplying both a registered rule and a city override is refused as ambiguous. Atomic physical footprints cannot carry a city perimeter rule.

The existing `BuildingSitePlanner.PlanBoundary` owns generation. It clips inward slabs to the owner's rectangular perimeter, at any rotation or winding. Native swept access/road polygons determine openings, including paths ending at the owner edge, parallel roads and corner crossings. Overlapping opening intervals merge with all contributing source IDs. Requested minimum width/clearance expands the opening within that edge; a minimum wider than the edge fails. No member or route is relocated and no vacant-position search is used. Adjacent edge slabs intentionally share their corner square, producing a connected perimeter. Openings are non-solid reservations with height zero; they do not create animated/closed gate assets.

`CityStructurePlacement.AccessWidthMeters` persists the engine's calculated access width, respecting city configuration and registered definitions. Validation checks it against resolved source facts. Native passage sweeps, boundary planning and schematic export use that same width. A registered facility also preserves an explicit external access width from its city type. The exporter no longer replaces all access widths with 1.5 m.

`ProceduralCityDocument.BoundaryElements` contains exact polygons, owner/rule/kind/purpose, height, `EdgeIndex`, opening flag and passage source IDs. Metadata uses owned `site-boundary`/`gate-opening` nodes and exact `MapGeometry` polygons, with side labels for inspection. Validation rebuilds the expected plan and rejects missing/forged geometry, flags, source IDs, heights, ownership, physical overlaps and altered access widths. Existing package regeneration and shared CLI logging/audit cover the new geometry and counts.

Rule limits: thickness 0.05–5 m, height greater than zero and at most 100 m, minimum opening greater than zero and at most 100 m, clearance 0–20 m. All values must be finite. The planner supports rectangular owners, convex swept passage pieces, at most 4,096 nearby pieces and a default 2,048 output elements per owner. Non-rectangular/infeasible owners fail explicitly. `MaximumBoundaryElements` defaults to 20,000 and accepts 1–40,000 across a city; viewer node/segment and package byte limits still apply. A perimeter that consumes a physical building is rejected rather than shrinking or moving the building.

The [site-boundary inputs](../examples/procedural-city/site-boundaries/) demonstrate inline, registered building and nested program rules using fence, wall, hedge and railings kinds. These are metadata kinds without artwork/material or runtime claims. Current aligned and 18° packets: `generated/procedural-city/site-boundaries-v4` and `generated/procedural-city/site-boundaries-rotated-v4`, each with 37 perimeter pieces and 13 openings. Camera focus now uses site-scale margins, and engine-coordinate zoom can inspect meter-scale details independently of total map size. Both preserve original polygons; SVG export retains the full map. [Evidence](SDLC_VERIFICATION.md#site-perimeters-and-declared-openings-2026-10-26). Runtime gates/animations, production artwork and owner city-design acceptance remain open.

## Compound sites and surroundings (2026-10-26)

`CityStructureType.SiteRules` reuses `BuildingSiteRule` for authored outdoor areas inside a compound envelope. Give a physical building surroundings by wrapping it in a reusable site with `Parts`; atomic footprints cannot carry these rules. Sites can contain nested sites with independent parts and grounds. The engine does not branch on names such as factory, campus or home.

The existing `BuildingSitePlanner.PlanCompound` allocates each rule's minimum-depth band in catalog order, leaving an inset member region for source-sized constituent packing. Front/rear follow the fixed entrance side; left/right follow the local site frame. Non-forecourt front bands preserve an entry gap. Required rules that cannot fit fail; optional infeasible rules leave no reservation. Existing internal margins/access still apply. The entire program rotates together into exact world-meter polygons without shrinking members or moving entrances.

`ProceduralCityDocument.SiteAreas` persists `PlannedSiteArea` owner, kind, polygon, rule and purpose; `SourceCatalog` retains the original authored city catalog. Validation resolves that catalog and regenerates areas, checking complete direct child membership, physical dimensions/kinds, containment, conflicts and access. Missing source inputs are rejected. `MaximumSiteAreas` defaults to 10,000 and accepts 1–20,000; this route limits a site to 64 rules with IDs up to 128 characters. The existing viewer's 5,000-node limit still applies to the complete exported hierarchy.

JavaScript renders areas as selectable children at the exported coordinates. Select a site, use **Focus selection**, then **Contained items → Open and focus item** to inspect nested structures or grounds; **Parent** returns through the hierarchy. Camera focus changes no polygon points. **Fit city** and SVG export retain the whole map and full district labels.

The [compound-sites inputs](../examples/procedural-city/compound-sites/) demonstrate manufacturing, learning-campus and home-site programs, including a nested utility site and 11 functional areas. The previous verified packet is `generated/procedural-city/compound-sites-v3`; it remains a snapshot of its recorded build. These zones establish functional land reservations, not fences, equipment assemblies, planted specimens, production artwork or runtime behavior. [Previous evidence](SDLC_VERIFICATION.md#compound-structures-and-surroundings-2026-10-26).

### Registered building surroundings

Set `IncludeCatalogSurroundings: true` on a `CityStructureType` with a `CatalogReference`, empty `Parts` and no inline `Footprint` or `SiteRules`. The selected registered `BuildingDefinition.SiteRules` now supplies the grounds directly. The generator derives a site envelope, adds a physical `building-0` child and passes both through the same compound planner. This is a one-building site reference; composition suggestions do not silently become constituent structures. Explicit compound `Parts` remain the way to author multiple buildings and nested source sites.

The derived envelope reserves the sum of minimum rule depths and insets on each band, plus physical dimensions and margins. The fixed center entrance remains clear even with asymmetric side bands. `MemberMarginMeters` defaults to 4 m and may be increased; source sites raise it to at least the selected variant's `SiteClearanceMeters` and the effective access width. `AccessWidthMeters` defaults to 2 m and source sites preserve at least the building definition's access width. Authored city values must be finite, margin 4–1,000 m, access 1–100 m and margin at least access. Source envelopes over 1,000 m or unsupported access/rule budgets fail explicitly. Unsupported linear/water-infrastructure references cannot masquerade as frontage sites.

Original catalog references and input hashes remain unchanged. `SourceStructures` records current registered definitions, variants and provider/content provenance for the site and its physical child. Metadata's compound node has `catalog_site_source`; its physical child has `StructureKey`, so consumers can distinguish reserved grounds from the building's actual size. Validation resolves the current registry and rejects altered source facts, dimensions or kinds. Package verification requires the same catalog registrations/content, then regenerates all derived types and geometry. `IncludeCatalogSurroundings: false` retains physical-only reference behavior.

The [catalog-sites inputs](../examples/procedural-city/catalog-sites/) reuse Modern workshop/home rules and a project-authored studio inside the manufacturing compound. `catalog-content.json` is an ordinary reusable content manifest. Saved project-content discovery or `--catalog-content` loads it for both `generate-city` and `verify-city`. Previous matching-build packet: `generated/procedural-city/catalog-sites`, 569 structure instances/225 areas. [Evidence](SDLC_VERIFICATION.md#registered-catalog-site-integration-2026-10-26). The separate facility reference below imports registered groups; neither route establishes resource/siting supplies or art/runtime acceptance.

### Registered facility programs

Set `CityStructureType.FacilityReference` to a `CityFacilityReference(Catalog, DefinitionId)`, with no physical `CatalogReference`, inline `Footprint`, `SiteRules`, `Parts`, open-space flag or `IncludeCatalogSurroundings`. This explicitly selects a registered `FacilityDefinition`, including templates produced by the existing reusable `FacilityProgramDefinition` authoring compiler. Original city inputs remain unchanged. A facility can be required at a center or nested as a part of another authored city compound.

`FacilityCompositionPlanner.PlanGeometry` is the neutral source owner. It traverses registered groups/offsets, retains exact slot polygons and component rules, and uses the existing `BuildingSizePlanner.PlanGeometry` and `BuildingSitePlanner.Plan` for each selected physical variant and its grounds. This is explicit geometry fitting; it does not invent a settlement demand/class/role or qualify simulation resource supplies. Existing demand-aware `BuildingSizePlanner.Plan` shares the physical fitting calculation and retains its demand checks. Source roads must support each member's declared minimum road width, and physical footprints must avoid roads and blocked access.

The fixed gate is the root's north-side center. A vertical connector joins the first intersected authored horizontal road; it must remain inside the source boundary. All authored roads, including nested templates, must already form a connected network with that connector. Missing entry intersections, disconnected roads and blocked/physically infeasible programs fail explicitly. The planner never searches vacant space, repacks source slots or invents missing child roads. Source templates retain their existing rectangular north/south frontage restrictions. Shared forecourts/circulation may overlap an access walk; ground reservations are not equipment or planting instances.

The city engine rotates and translates the entire source plan into its selected frontage frame. Every source group is a compound, each slot is an owned building site, and each physical building is a distinct child with source-sized geometry. `SourceFacilities` retains registered template/plan/provenance snapshots; `SourceStructures` retains selected building facts. `FacilityRoads` has actual owner/root/source-road IDs, centerlines, profiles and classes. These internal roads do not enter `Streets` or redefine the city's block partition. Validation recompiles the source and compares member geometry, membership, grounds and roads; package verification reproduces the original inputs with the same registered content.

Metadata exports `FacilityDefinitions`, source links, owned road nodes and exact centerlines/polygons. Friendly building names and member purposes appear in the viewer. Engine-coordinate roads use native SVG butt caps to preserve their authored endpoints; camera focus and SVG export change no physical polygons.

Limits: each neutral plan is bounded to 1,000 groups/buildings and 1,000 authored roads plus its entrance; recursive groups are bounded to depth 16, and city hierarchy/structure budgets still apply. Derived type resolution caps at 10,000 types. City facility envelopes over 1,000 m per axis are refused. `MaximumFacilityRoads` defaults to 10,000 and accepts 1–20,000; viewer node/segment and package byte limits still apply. Template fitting and connection support are explicit constraints, not unrestricted facility synthesis.

## Context-driven city candidate

`CityDesignIntent.Boundary` optionally supplies a `CityBoundaryRule`: an ID/purpose, simple polygon in world meters (including inward notches), symmetric perimeter-road profile and registered road role. `CityBoundaryPlanner` clips the selected source network, replaces coincident perimeter roads, and retains only entrance paths from a shortest-path forest rooted at perimeter crossings. Original hubs stay fixed; source road IDs and boundary-rule provenance survive export. The perimeter must contain all hubs and remain within the source development footprint. Its polygon describes the perimeter street centerline; roads reserve width on both sides. [Boundary example](../examples/procedural-city/bounded-footprint/request.json).

Concave street faces are partitioned by continuing visible incident edges from reflex corners to the nearest opposite street. Candidate splits must reduce reflex corners; scoring favors fewer remaining concavities and smaller geometric deficits before shorter streets. Existing streets are reused when faces are already convex. The common parcel planner can retire an infeasible frontage row and recompute all frontage distance cells, retaining complete land allocation and exact catalog dimensions. [Concave example](../examples/procedural-city/concave-footprint/request.json). Added streets are recorded in `CityNetworkAdjustment.AddedSegments` with purpose/rule provenance; removals remain in `RemovedSegments`.

`MergeSmallBlocks` defaults to true. Perimeter faces narrower than `MinimumBlockSpanMeters` in supporting width or geometric side length, or whose road reservation collapses, are merged across eligible interior local shared streets. Main/collector roads, hubs, perimeter streets and actual exterior entrance paths are protected. A merge may use continuation streets to restore convex faces; accepted plans remain connected and strictly reduce total span/collapse deficit. If no valid repair exists the engine fails explicitly, with the unresolved `BoundaryFace` in exception data. `NetworkPlan.Adjustments` and root metadata `generation_adjustments` record street changes; CLI/audit and `summary.json` disclose their count. Set false to disable small-block merges (concave-face partitioning remains required); later parcel-fit checks can still fail. [Repair example](../examples/procedural-city/boundary-repair/request.json). These are game-authored geometry rules, not real-world planning standards or guaranteed fitting for every catalog. Terrain holes, non-convex individual parcels and automatic obstacle avoidance remain open.

`GuidedCityNetworkLayout` (`guided-corridor`) adds a route-shaped lattice: `Parameters(halfLengthMeters, halfDepthMeters, targetBlockLengthMeters, targetBlockDepthMeters, guide, rotationDegrees)` takes ordered local-meter `(longitudinal, lateral-offset)` guide points spanning the declared length and including `(0,0)` at the primary hub. Each bend and hub introduces a street station; parallel roads follow the guide, with connecting cross streets. Guide points must be at least the requested minimum block span apart and slopes stay within ±1; infeasible hub spacing and map extents fail explicitly. This produces piecewise-linear convex blocks through the common parcel/structure pipeline, not terrain avoidance or unrestricted organic growth. [Reusable request](../examples/procedural-city/guided-corridor/request.json).

For game-map code, register `RadialCityNetworkLayout` and/or `GridCityNetworkLayout` through `ICityNetworkLayout`. The same generator handles hubs/entrances, district programs, polygon parcels, source-sized rotated buildings, constituent structures, required sites and parks. Each strategy parses/validates its own `CityDesignIntent.LayoutParameters`; use `RadialCityNetworkLayout.Parameters(...)` or `GridCityNetworkLayout.Parameters(...)`. Shared generation contains no strategy-name switch. See the current [radial](../examples/procedural-city/contextual/request.json) and [grid](../examples/procedural-city/planned-grid/request.json) requests. This is a game-developer tool; real-world traffic/economy/infrastructure simulation is optional. [Code verification](SDLC_VERIFICATION.md#game-map-network-code-2026-10-26). Other patterns, terrain, native runtime and composition acceptance remain open; the API section below describes the single current pipeline.

## Research and replacement direction (2026-10-26)

Scope: online research requested by the owner after rejecting the whole district/city algorithm. This is a design recommendation, not a newly implemented generator or a claim of a universally best algorithm. Primary papers and official documentation were consulted on 2026-10-26. Publication years below come from the publications, not search-engine crawl dates.

### Observed failure in this engine

`ProceduralCityGenerator.Generate` partitions districts by area weights along the longest rectangle axis; district purpose does not affect those cuts. Both registered street strategies subdivide rectangles. The block index selects one structure type for every parcel in that block, and a modulo rule selects park blocks. Every street uses the same cross-section. A depth cap in `CityFrontageParcelPlanner` creates courtyard reserves wherever frontage strips leave an interior; it does not establish a city-level reason for those courts.

Inspection of `generated/procedural-city/enhanced/mixed-frontages/city.json` found 28 blocks, 23 development blocks, all 23 using a single root structure type per block, 18 courtyards, five parks and one 9.5 m street cross-section. The saved browser capture shows the repetitive hollow-block composition. These observations explain the implementation defect; they are not universal limits on how many courts, single-use blocks or grids a game may intentionally request. Grid streets remain a valid style. Arbitrary curves or randomness would not fix the missing composition.

### Recommended synthesis for this engine

The recommendation is a **goal-driven street graph with tensor-field guidance and program-specific polygon parcels**, with optional structured example guidance. This is an engineering synthesis of the methods above, not a single published algorithm or a benchmark result.

1. **Create the city brief and context.** Resolve game scale, settlement footprint, buildable/excluded land, approach connections, intended centers and significant sites from reusable rules. Infer reversible defaults from the request; do not require a mockup or individual building coordinates. These become explicit engine inputs/intermediate facts with purposes.
2. **Plan the main connections.** Connect declared centers, approaches and significant sites through major routes. Generate local roads under separate density, spacing and directional policies. Record why a route exists. Do not require a perimeter road around every map or major roads on every district boundary.
3. **Coordinate districts and streets.** Assign/adjust district programs using centers, accessibility, boundaries and authored compatibility rules, with bounded feedback when the network or program cannot fit. Districts are not fixed strips produced before context is considered. Land-use choices remain game-authored policies rather than a hardcoded list of modern-city districts.
4. **Derive actual blocks.** Build planar faces from the street graph, account for street widths and excluded land, and retain boundary-edge/road ownership. Keep grade-separated crossings distinct. Reject invalid/sliver faces according to explicit tolerances; do not replace polygons with bounding rectangles.
5. **Choose block and parcel programs.** Support street-facing back-to-back lots, perimeter blocks with explicitly requested courts, large unsplit sites and other registered programs. Subdivide according to usable frontage, catalog/site needs, access and density. Place significant unique facilities by declared counts/roles; do not repeat them merely because their type appears in a cycle. Parks and open areas get planned relationships, not every-Nth-block placement.
6. **Fit catalog buildings and compounds.** Preserve reusable arbitrary constituent structures. Calculate orientation and access against actual frontage segments; validate the entire site program without shrinking catalog dimensions or searching vacant cells.
7. **Review the city before downstream export.** Show exact C# output in JavaScript at overview and block scale. Keep structural validity, design intent, observed composition and owner acceptance separate. A package integrity pass must not certify believable design.

### Implementation implications and next acceptance gates

Keep the existing `ProceduralCityGenerator` as orchestration owner and variants behind shared contracts. Reuse the existing polygon/polyline, topology, catalog, validation, package and reporting owners. `CityRegion`, `CityBlock`, `CityParcel` and `MapGeometry` currently assume rectangles/cardinal sides; they must represent polygon boundaries and actual frontage edges before claiming organic/radial support. Adding an `OrganicCityLayout` behind the current rectangular partition contract would preserve the core defect. Do not introduce a second city save format or implement generation in the JavaScript viewer.

Next composition delivery requires explicit centers/approaches, road roles, polygon block contracts and one end-to-end contextual request, followed by multiple pattern profiles. Exact street/parcel algorithm parameters and any geometry dependencies require implementation-level review before adoption. Preserve current packets as rejected baselines. Do not regenerate only a prettier screenshot and label the pipeline fixed.

Acceptance must demonstrate: main routes joining the declared anchors; district/program relationships reflected in geometry; no forced court/park/index cycle; access-aware valid polygon lots; required facility counts and nested programs; explanatory intermediate data; deterministic regeneration; and observable differences between a planned grid, a radial-center layout and a constrained irregular layout. All cases need street/block/parcel overview inspection plus close views, including deliberate failures. These are proposed evaluation profiles, not a fixed supported-world list. The contextual street/district/parcel redesign, runtime performance, composition quality and owner acceptance remain **NOT IMPLEMENTED / NOT VERIFIED** by this research. The geometry foundation implemented afterwards is scoped below.

## Street-derived polygon foundation

`UrbanBlockExtractor.Extract(corridors, maximumBlocks, cancellationToken)` now uses the existing `StreetTopologyBuilder` and directed half-edge traversal to find bounded planar faces. It no longer scans global X/Y intervals for rectangular loops. The extractor retains the street-centerline face in `UrbanBlock.StreetBoundary`, its reserved buildable polygon in `Boundary`, and the actual directed road/frontage segments and road-side offsets in `Frontages`. Each edge uses its corridor's cross-section, including left/right asymmetry. Input order is normalized; polygon coordinates and edge provenance determine the block identity.

The existing generator now creates the complete street network before assigning parcels. Declared rectangular block programs must correspond one-to-one to actual extracted faces. Their `CityBlock.Geometry` is persisted and validated against fresh street extraction; forged geometry/areas/ownership or stale bounds fail validation. Existing rectangular parcel programs explicitly reject nonrectangular interiors instead of using a bounding rectangle as buildable land. This is a required foundation for replacing the rejected city model, not an implementation of center-driven street growth or arbitrary polygon lots.

`MapGeometry.Polygons` supplies exact node polygon vertices to the existing schematic. Bounding boxes remain selection/layout bounds; a supplied polygon is rendered as SVG polygon geometry. Missing optional polygons retain rectangle semantics for metadata that actually declares rectangles. Malformed, duplicate, out-of-bounds and self-intersecting polygons reject. Polygon labels use explicit node positions; the concave diagnostic's engine-authored anchor is inside a triangulated face rather than in its bounding-box void. Browser selection and SVG export retain actual vertices.

Extraction is bounded/cancellable and returns no partial blocks when diagnostics exist. Supported faces are simple polygons whose directed edge offsets remain a single simple interior without collapsed/reversed edges. Interior cul-de-sac spurs, multiply connected faces/holes, collapsed offsets and straight edges with width transitions that require extra join geometry explicitly diagnose. Disconnected/overlapping street graphs are rejected through existing topology diagnostics. Grade-separated crossings are not represented by this planar input contract. Asymmetric widths are verified at extraction level; the current city parcel/line-rendering route is not qualified for asymmetric profiles. This is not a general polygon-union or skeleton implementation.

Focused tests cover the missing T-junction block, diagonal and concave shapes, per-road and asymmetric widths, actual crossing splits, corridor order invariance including nonintegral intersections, invalid interiors, budgets/cancellation, generation/persistence/tampering and exact rendering. `generated/procedural-city/polygon-foundation/diagnostic-current` is an authored-street **geometry test fixture**, not a generated city; the old rectangular generator has been removed. This diagnostic does not establish city-design acceptance. [Current verification](SDLC_VERIFICATION.md#street-derived-polygon-block-foundation-2026-10-26).

## Generation

1. Resolve the required `CityDesignIntent`: centers, approaches, registered network parameters, road profiles, required sites and parks.
2. Generate the shared city street network through `ICityNetworkLayout` and apply any authored city perimeter.
3. Extract actual polygon street faces, reserve road widths and assign districts by center influence.
4. Allocate declared required sites/parks; subdivide remaining convex blocks through district frontage/mix programs.
5. Fit unscaled catalog footprints in road-aligned local frames. Compile registered facilities through `FacilityCompositionPlanner.PlanGeometry`, preserving nested ownership, source slots, roads and surroundings.
6. Validate actual partition, dimensions, containment, collisions, access, budgets and source provenance before publishing.

No vacant-position search, arbitrary scatter, weighted rectangular district cuts or block-index cycling exists in the current pipeline. Infeasible required content fails explicitly.

## API

Contracts are in `WorldCreator.Core.Cities`; algorithms are in `WorldCreator.Worlds`.

```csharp
var generator = new ProceduralCityGenerator(
    [new RadialCityNetworkLayout(), new GridCityNetworkLayout(), new GuidedCityNetworkLayout()],
    optionalCatalogRegistry);
ProceduralCityDocument city = generator.Generate(request, catalog, cancellationToken);
IReadOnlyList<string> issues = generator.Validate(city, cancellationToken);
WorldMetadataDocument metadata = generator.CreateMetadata(city, cancellationToken);
await generator.GenerateFilesAsync(requestPath, catalogPath, newOutputDirectory, cancellationToken);
```

Hosts register `ICityNetworkLayout` implementations. Each strategy validates its own `LayoutParameters`; generation has no strategy-name switch. Use the strategy's `Parameters(...)` factory.

## Rules and catalog

`ProceduralCityRequest` supplies dimensions, local street profile, minimum block span, setback, district programs, mandatory `Design`, coverage and budgets. Each `CityDistrictRule` supplies ID, purpose, center-influence weight and `Program`. Block size belongs to network parameters; parcel density belongs to each district program. Every parcel retains its actual polygon and frontage endpoints; every structure retains an exact polygon and rotation.

The rejected rectangular generation controls and mockup-only facility expansion/state are deleted. Removed JSON fields fail at the current request boundary. There are no obsolete-ID aliases, optional old generator or automatic geometry conversion. Update callers to the current contracts and regenerate packets; saved historical outputs remain evidence of their original builds.

`ProceduralCityCatalog` defines reusable types and nested constituent programs. Game-authored footprints use origin 0,0 and positive dimensions. `CatalogReference` resolves registered source dimensions and provenance; `FacilityReference` resolves a registered nested program and its exact geometry. No duplicated measured facts or fabricated simulation resources are required. The geometry pipeline does not certify supply simulation, artwork or playable runtime behavior.

## Output and rendering

`ProceduralCityDocument` retains the request/digests, district boundaries, road centerlines/profiles, connected street graph, blocks, parcels, source ownership, entrances/access paths, structure footprints and parks. File export publishes into a new directory using staging and a final directory move:

- `request.json`, `recipe.json`, `catalog.json`: generation inputs (`recipe.json` is a viewer-compatible alias of the city request).
- `city.json`: engine city plan, including exact geometry and topology.
- `summary.json`: counts, coverage, connectivity and provenance.
- `world-metadata.json`: derived hierarchy/relationships with optional `MapGeometry`.
- `schematic.html`, `schematic.js`: JavaScript/SVG viewer.
- `package-manifest.json`: byte hashes/lengths for the eight files above and exact engine/Core assembly identities. Publication refuses any file over 16 MiB, matching the current strict package reader.

`VerifyFilesAsync(directory)` / `verify-city <package-directory>` rechecks a published packet without modifying it. It accepts only the fixed file inventory, rejects linked roots/files, checks hashes and the engine build, regenerates the city from saved inputs and compares city geometry, metadata, summary, recipe and expected viewer sources. Changing a manifest hash does not make forged geometry or viewer code reproducible. API source-catalog references require the same registered catalogs; CLI catalog flags work as for generation. Older packets without a manifest and packets from different builds are not silently certified. This is reproducibility/integrity evidence, not a signature, external approval, art acceptance or proof of who authored inputs.

The `MapGeometry` field is authoritative when present. The viewer draws those rectangles, road segments and widths in meter coordinates; changing presentation-grid hints does not alter placement. Corrupt spatial data is rejected, never replaced with diagram packing. Earlier metadata-only recipes still support their separate presentation layout.

CLI generation uses shared log/audit/notification services, including failures and cancellation. Existing destinations are refused. API callers own their host reporting. Inputs use the existing strict JSON reader and generation is bounded/cancellable. IDs are structural identifiers, not file paths.

### Ordered multirow frontage programs

`FacilityFrontageGrammar.MaximumRowSpanMeters` sets the usable span for members and their declared inter-site gaps; outer margins and the shared side aisle are additional. A missing span means one unbounded row in the same staged compiler. `InterRowGapMeters` (default 8) reserves separation between the previous row's member bounds and the next row's full native road surface. Parts expand in declaration/count order, followed by child facilities in declaration/count order. A member wider than the declared span fails with `CATALOG_FACILITY_MEMBER_EXCEEDS_ROW_SPAN`; physical variants never shrink or move into a vacant-space fallback.

Rows share a native-width side aisle. Every child keeps its exact internal slots, roads and offsets, receives a declared placement below the parent frontage, and connects through its north-center gate to its own entry road. The parent link uses that entry's native road profile, even when the child has a different road offset/profile. Root assembly and child linking share one entrance rule with fully qualified source-road ordering. Child-only, object-only, ground-only and mixed programs use this same grammar. Full route sweeps, source ownership, clearance, source regeneration, budgets and cancellation remain validated. This is an ordered frontage grammar, not unrestricted facility packing, interiors or traffic simulation.

The [multirow example](../examples/procedural-city/facility-rows/catalog-content.json) has two mixed parent rows plus two rows in each nested object/ground precinct. Current matching-build packets are `generated/procedural-city/facility-rows-v2` and `facility-rows-rotated-v2`. The source parent measures 167.4 × 168.7 m, with one structure, four objects and four standalone grounds; rotation preserves those dimensions. [Verification](SDLC_VERIFICATION.md#ordered-multirow-facility-programs-2026-10-26) records API/CLI/package, independent JavaScript and browser/SVG checks. This does not certify whole-city design approval, artwork or native runtime.

### Compact required-site allocation

Required sites use `CityFrontageParcelPlanner.PlanRequiredSite`: reserve the fixed source envelope plus declared setbacks, then subdivide the original street-fronted remainder cells using the district's authored mix. The original block and streets remain authoritative. Clipped buildable frontages retain the original road's actual centerline span; cut edges never become invented streets. A single-frontage cell is supported, including rear corner wedges wider than its finite street projection. The first/last parcels own those wedges while their access/frontage remains on the actual street segment.

At most three unusable side/rear strips can merge into the required site's perimeter. A strip is unusable only when no permitted source type can fit through its real frontage; feasible remainder land is never absorbed to bypass a planning failure. Infeasible allocation refuses explicitly. `CityDistrictProgram.WholeBlockSites=true` remains an explicit game-authored whole-block program, rather than an automatic required-site fallback. Validation rebuilds required-site partitions and rejects forged boundaries, frontages, membership or missing remainder parcels. Block coverage, no-overlap, source dimensions, route clearance, budgets/cancellation and package reproduction remain enforced.

### Ordinary plot depth and feasible source mix

`CityDistrictProgram.MaximumParcelDepthMeters` is an optional game-authored limit (finite 4–30,000 m). It measures the maximum perpendicular distance from a parcel's actual street frontage to its polygon vertices. It applies to ordinary plots, including explicit whole-block ordinary programs; required physical sites have their own envelopes. Null declares no cap. Generation and persisted validation enforce it, and metadata exports `parcel_depth_meters`, `maximum_parcel_depth_meters` where applicable, and `required_site`. An incompatible street/site design refuses with `CITY_PARCEL_DEPTH_EXCEEDS_LIMIT`; it does not manufacture roads, shrink source geometry or absorb feasible land to bypass the cap. Removing a frontage cannot repair an already excessive nearest-street cell depth.

Frontage and lot eligibility use each permitted source's actual width/depth and setbacks, rather than combining the largest width and depth of different types into a fictitious template. A frontage that cannot fit any allowed source in the full cell never takes land from viable opposite frontages. Each lot retains only types that fit its polygon and actual road binding. The district-wide allocator matches these feasible types across all ordinary parcels. Weights are preferences; `MinimumCount`/`MaximumCount` impose hard ordinary parcel counts. Named anchor-bound facilities still belong in `RequiredSites`. Single-building catalog sites use direct access; multi-building sites retain their shared aisle.

The [ordinary-site example](../examples/procedural-city/plot-programs/request.json) authors a 60 m cap, 230 × 120 m target street spacing and registered house/market/workshop surroundings. Its rotated counterpart rotates its authored hubs with the street frame; retaining fixed hubs can introduce incompatible extra street intervals and is tested as a refusal. Matching-build packets: `generated/procedural-city/plot-programs-v2` and `plot-programs-rotated-v2`. Both have 60 blocks; maximum ordinary depth is 55.25/51.25 m, respectively. Catalog physical variants remain unchanged. External content must also be supplied to `verify-city --catalog-content <manifest>` unless discovered from saved project content.

The aligned ordinary plots still have 79.6% of their aggregate area outside the root building-and-surroundings envelope (previous compact snapshot: 90.4%). This is an unprogrammed-area measure, not a building coverage or visual-completeness score. Uniform frontage subdivision widens every lot when corner lots fail, and the fixed source program does not expand into the remaining rear/corner parcel land. Those are remaining composition defects; a depth cap and a small garden do not resolve them. ### Corner-sensitive frontage subdivision

The shared `BuildingEnvelopePlanner.FixedFrontageCenters` computes the exact feasible center interval for an unscaled rectangle at the frontage setback. `PlanFixedFrontageFootprint` uses the midpoint of that same interval; subdivision uses its extrema. `CityFrontageParcelPlanner` intersects those intervals with real finite road/buildable frontage spans to determine the minimum corner reservation. Middle plots follow the district target, subject to individual physical fit. Small remainders are shared between the ends, rather than introducing a sliver. A failing interval may coalesce with its immediate neighbor; the planner prefers a feasible merged pair and then the shorter span. Every coalescing step removes one cut. Other fitting intervals retain their cuts. There is one current row planner; the old loop that repeatedly widened every row parcel is removed.

Complete rear wedges remain owned by the end parcels, including portions beyond finite frontage projection. No cut becomes a street. Actual gate binding, per-lot eligible types, depth cap, source dimensions, full coverage, overlap refusal, cancellation and existing budgets remain authoritative. The interval calculation chooses cuts from source geometry constraints; it does not scatter structures, search for vacant positions, invent props or resize a source.

Regenerating the unchanged ordinary-site example produces `generated/procedural-city/corner-parcels` / `corner-parcels-rotated`. Both retain the original sixty blocks and twenty-two streets, with 873/841 total parcels and 1,767/1,703 structure instances. Ordinary plot counts rise from 610/586 to 870/838. Aligned median frontage falls from 64.29 to 45.23 m; rotated from 60.96 to 40.78 m. Ordinary root-program area coverage rises from 20.4%/22.3% to 28.8%/31.7%, with source physical definitions and variants preserved. Catalog implementation/content identities change honestly with the engine build.

This corrects corner-driven row-wide enlargement, not all open land. Remaining unprogrammed ordinary parcel area is 71.2% aligned / 68.3% rotated. Complete purpose-bearing rear-land composition is further shared engine/catalog work; greenery or colors must not conceal the gap. ### District-wide content allocation

The current `CityDistrictAllocator` replaces the traversal-order per-parcel choice loop. It treats every ordinary parcel in a district and its feasible source types as one constrained assignment. `CityLandUseRule` supports `MinimumCount` (default 0) and nullable `MaximumCount`; these counts exclude explicit `RequiredSites`. A zero maximum also excludes the type from ordinary parcel geometry planning. Road-role restrictions and exact physical source fit remain mandatory.

Minimum counts are satisfied first. Alternating paths can move a flexible assignment to another eligible parcel to free a scarce site without losing an already satisfied type count. Remaining parcels follow weighted marginal allocation subject to upper bounds. Candidate/rule enumeration order does not select the result; ordinal IDs resolve ties. The generator uses this one allocator for every city network strategy, with no greedy fallback.

Infeasible constraints throw `CITY_DISTRICT_DEMAND_UNSATISFIED`; bounded search throws `CITY_ALLOCATION_SEARCH_BUDGET`. Both flow through the existing failed-generation/audit boundary without publishing partial output. Saved-city validation checks achieved quotas, and package reproduction compares the actual result. District metadata includes `land_use_allocation` with scope, algorithm, each declared weight/bound and actual count.

The `examples/procedural-city/district-demand` input demonstrates exactly six ordinary shops in the residential district, alongside separately declared required sites. These are synthetic game inputs, not a complete game design. See `CITY_GENERATION_RESEARCH.md` for sources, the architecture and remaining density/topology/world-variety requirements.
