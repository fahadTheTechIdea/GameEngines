SimEngine

A deterministic simulation kernel for colony, tycoon, logistics and process games: modules, systems, entities and components, authored JSON content, work and resource transactions, maps and navigation, production, logistics, incidents, knowledge, objective progress, save/hash and lockstep replay.

Purpose

SimEngine simulates a world over time: entities with components, systems that run on a schedule, resources and promises, work jobs and workers, production processes, logistics, incidents, knowledge, objectives and spatial maps. It is engine-independent: no renderer, platform SDK or game assembly dependency. A game is a GameDefinition of modules plus authored JSON content.

Simulation first

Money, markets and Tycoon rules are an optional module. Resource-only survival and colony games run without them.

Deterministic core

Fixed-point gameplay maths, stable IDs and order, one seeded random source, one game clock, and one Sync per stateful owner.

Extend, never parallel

New behavior extends the existing registries, stores, codecs and projections. A second scheduler, clock, stock ledger or state owner is a defect.

Architecture

GameDefinition            modules + content types
   ↓
ContentSet.Load(source)   manifest → JSON defs → ResolvedContent
   ↓
GameFactory.NewGame(...)  World + modules composed, scenario, startup
   ↓
SimGame / World           one clock, systems, entities, services, commands
   ↓
PlayerSeat                commands in, results/notifications/views out
   ↓
SaveGame / Replay / Lockstep
  • World owns content, settings, seeded random, entities, events, services, players, commands, the fault gate and the sole clock.
  • GameModule declares content types and composes systems, services, commands, map layers, world-generation stages and view features.
  • GameSystem runs on a Schedule (every tick, periodic, or spread across entity buckets).
  • Hosts read immutable views/snapshots, submit commands and drive Initialize/Update. They never touch mutable world state.

Modules and systems

Built-in modules include:

ContentAccess, WorldSetup, Work, WorkSignals, Inventory, InventorySignals, Logistics, LogisticsRecoveryPolicy, DispatchPolicy, Motion, Infrastructure, Transformation, Construction, Technology, KnowledgeVisibility, CompanyKnowledge, Exploration, IncidentResponse, IncidentProcess, IncidentPropagation, ScenarioPressure, Objective, PlayerControllers, Automation, CompanyAlert, MachineFleets, PlanHistory, GameConditions, EnvironmentalMetrics, ResourceFlows, SpatialResources, TileNavigation, TileConditions, TileConstructionRules, TileTerrainWork, Weather, EquipmentCondition, Character, UtilitySignals, RemoteSignals, EventDispatchPolicy, LockstepPolicy, Operations, and the optional Tycoon economy module.

A module add-on is code-availability and dependency only; all startup and gameplay intent is authored JSON. Content is selected through the master manifest; a missing or invalid definition fails explicitly rather than becoming a hidden default.

Entities, components and defs

EntityDef  (authored prototype)
   └── ComponentDef / ComponentDef<T>   (capability fields)
Entity     (live instance)
   └── Component / Component<TDef>      (state + behavior)
  • Entities are created through World.Spawn(def, owner, configure); removal goes through guards (CheckDespawn) so stock, promises and claims are never silently discarded.
  • A component carries one responsibility and one Sync for its state. Related behavior lives in partial files of the same owner, not a new service.
  • Entity.Update is the only place a component's resolved state is committed; systems operate on live entities through their existing owners.
  • Multi-part lifecycle hooks (IEntityInitialization, IEntityRemovalGuard, IEntityReplacementState) are not entities or capability slots.

Authored content

  • A manifest.json lists modules and their documents. ContentSet.Load(source, types) reads and resolves them into ResolvedContent.
  • Every definition is a Def registered against a section and capability key; strict JSON readers live in the definition or its declaration, not in a game host.
  • Definitions are validated and frozen before publication. Missing references, duplicate identities, ambiguous capability keys and invalid metadata refuse before Initialize.
  • Scenario JSON declares a time quantum, game mode, modules, startup/world setup and initial entities. There is no implicit scenario time or hidden default world.

Work, resources and production

  • Work is an activity graph: activities contain nodes with executors, roles, durations and requirements. WorkBoard owns evaluation, jobs, spending, progress and history; WorkSystem owns matching, travel and physical execution.
  • Resources are exact quantities with units; inventory ownership is one ResourceInventoryState, and promises are owned receipt records. ResourceTransactions is the sole transfer/claim/conversion authority.
  • Logistics owns demands, stock bands, routes, carriers, loading/unloading and recovery; it is not a separate scheduler.
  • Production (Transformer/TransformerManager) consumes inputs and time, keeps WIP and tools, and commits whole results; continuous and batch modes are authored explicitly.
  • Construction uses a site, a work graph, real materials and timed completion; removal goes through recovery/disposition.
  • Tycoon is optional: values, accounts, income, monetary costs, suppliers and advanced rules. No money is required for unpriced physical work.

Maps, navigation and space

  • MapLayer/MapLayer<T> store sparse typed values (byte, int, fixed) and own their codec, invalidation and privacy.
  • TileMap is the native tile space; independent point-space providers implement the same spatial contracts without being forced into tiles.
  • ITileNavigationRule, LayeredTileNavigation, NavGrid and PathSearch own routing; Mover owns actual motion, fractional position, route checks and fuel/exposure gates.
  • Regions, areas, docks, placement, occupancy and visibility are provider-owned contracts; no host interprets geometry.

Simulation lifecycle

var definition = QuickModule.CreateDefinition();
var files    = new DiskFileSource(Path.Combine(AppContext.BaseDirectory, "Content"));
var factory  = new GameFactory(definition, ContentSet.Load(files, definition.ContentTypes));
var game     = factory.NewGame(new NewGameRequest { Scenario = "quick", Seed = 42 });
game.Initialize();
game.Update();                       // one deterministic engine-time step
ulong hash   = game.Hash();
byte[] save  = game.Save();
var back     = factory.Load(save);
  • NewGameRequest: scenario, seed, seats/controllers, spectate, horizon, mods and typed game-mode overrides.
  • SimGame.Seat(i) gives a PlayerSeat: Submit, Preview, ReadResults, ReadNotifications, Snapshot, View.
  • A failed system or provider faults the session; no later phase runs and the world cannot be saved or hashed as healthy.
  • GameClock is the only current time. World.Step advances it after successful gameplay; every duration derives from the authored quantum.

Determinism, save, hash and replay

  • Fixed-point gameplay maths, stable entity/component ids and canonical ordering. No wall clock, floating-point gameplay or platform-timing decision.
  • Every stateful responsibility has exactly one Sync(IStateSync) that owns save, load and hash.
  • World.Hash() / HashBreakdown() give the canonical state digest; saves carry build, scenario and seed identity and refuse incompatible or corrupt data.
  • SimGame.RecordReplay(limits) records admitted inputs and verifies hashes and results; lockstep sessions compare peer state.
  • Faulted, pending or mid-commit states cannot checkpoint. Saves are never migrated by guessing.

Hosting and GameRuntime

GameRuntime.Sim wraps SimEngine in a runtime component: SimComponent drives the world, SimEffectDispatcher applies mission effects, SimEventOutbox publishes world events, and DirectorBridgeModule bridges scenario pressure. Headless proofs (GameRuntime.Field.Headless, GameRuntime.Briefing.Headless, GameRuntime.Headless) show complete sessions without a renderer.

Build and verification

dotnet build src/SimEngine/Beep.SimEngine.slnx -c Release
dotnet run --project src/SimEngine/help/quickstart/Host/QuickGame.Host.csproj -c Release

SimEngine's rule is focused verification: build when compilation needs checking, run only the affected suite for a completed slice, and keep the broad regression gate open until explicitly authorized. Stage evidence is recorded under docs/migration with exact commands, identities and limits; counts and focused cases are not a full-suite claim.
