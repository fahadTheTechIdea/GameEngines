Purpose

GameRuntime is the orchestration layer between the pure engines and a host. Each engine gets a component that translates events into engine calls and engine changes into events. The session runs ticks, calls every component in a fixed order, drains the events each one emitted before the next runs, and settles the tick.

It owns

Tick order, the clock, the event bus, request channels, component lifecycle, fault reporting, checkpoints, journals and replay.

It does not own

Game rules. Every rule lives in an engine core; a component must not add thresholds or target rules.

Fail-stop

An exception stops the session, is reported once through IRuntimeReporter, and raises SessionFaulted. Nothing continues on inconsistent state.

The component contract

public interface IGameComponent
{
    string Id { get; }
    void Init(in ComponentContext context);   // like Godot _ready: connect, declare, no work
    void Update(in UpdateContext context);    // like _physics_process: one tick
}
  • UpdateContext gives the tick (first tick is 1), the real tick duration, an interpolation Alpha and total game microseconds. Components never own a counter.
  • Init connects events; Update does the work. Connecting after init is refused.
  • A component reads only its own state and the events it was given. It does not reach into another component.

Session and tick order

var clock   = new RuntimeClock(ticksPerSecond: 60, catchUpCap: 8);
var session = new RuntimeSession(clock, reporter);
CalendarChannels.Install(session);        // declares events and adds the registry last
session.AddComponent(calendar, order: 10);
session.AddComponent(economy,  order: 20);
session.Init();
int ran = session.Update(elapsedMicroseconds);
  1. Deliver queued input events.
  2. For each component in ascending order: run Update, then drain the events it emitted (handlers run in connection order).
  3. Emit TickSettled and drain once more.
  4. If an ending was requested, enter Ended and discard pending time.

Orders and component ids are unique; the session is Created → Running → Ended / Faulted / Disposed. Update returns how many ticks ran, bounded by the catch-up cap.

Clock and pacing

MemberMeaning
RuntimeClock(ticksPerSecond, catchUpCap, startTick)Exact integer accumulator; the division remainder is carried, so there is no drift.
SetSpeed(n, d)Rational speed, each 1..64 (half, double, …).
Pause / ResumeWhile paused no tick is earned.
Earn(elapsedMicroseconds)Earns whole ticks, bounded by CatchUpCap; IsRunningSlowly says the host fell behind.
Alpha, PendingTicks, TickInterpolation and backlog for the host.

EngineMainLoop.Run(host, totalMicroseconds, fixedFrameMicroseconds, writeInputs) is the engine-style loop for a console, test or server. A fixed frame feeds virtual time, which makes a run reproducible; a null frame reads the real clock.

Events and input

  • IEventPort.Emit<T> queues a struct event; it is delivered after the emitting Update returns, in publication order. Connect<T> is allowed during Init only.
  • The bus has a per-drain budget; exceeding it is a fault, not a silent drop.
  • Hosts Subscribe<T> to events; delivery happens after the tick's drain, never during it.
  • Submit<T> queues input for the start of the next tick; InputState + InputStateBridge turn pressed/released edges into pollable action state.
  • Standard events: observation posted, mission command requested, mission event, effect requested, command resolved, tick settled, session faulted, session ended, input edge raised.

Request channels

ChannelRegistry is the single registry every request-serving component uses. An engine's channels are declared by its Install(session), which also adds the registry as the session's last component.

  • Every request gets an answer in the same tick: from the serving component, or from the registry as the engine's refusal event with the unknown-channel code.
  • Two components on one channel are refused at Init (duplicate-channel code).
  • A component whose registry is not running fails its first Update — its requests could not be answered.
  • IsQuiet is false while a refusal waits, so a checkpoint cannot be taken between a request and its answer. The channel set is fixed at assembly, so it is the same on replay.

Bridges (.Economy.Bridges, .Diplomacy.Bridges, .Relationship.Bridges, .Tutorial.Bridges, .WorldEvents.Bridges, .Calendar.Ai) translate one engine's events into another's requests. A bridge holds no rule of its own.

Journal, checkpoint and replay

  • SessionJournal records inputs and per-tick state hashes; Serialize/Deserialize round-trip it. JournalComponent writes the hash each tick.
  • JournalingRuntime wraps any IGameRuntime and records inputs transparently.
  • JournalReplay re-runs a journal and returns ReplayResult(Matches, DivergedAtTick, Code); a divergence names the first tick that differs.
  • CompositeCheckpointService combines the mission snapshot with each engine's checkpoint parts; a checkpoint is refused (CheckpointRefusedException) when a component is not quiet.
  • Each engine component has its own checkpoint helper and Fingerprint() for diagnostics.

Hosts: console, headless, Godot

  • Console/server — EngineMainLoop with a fixed or real frame and OutputLog for text output.
  • Headless proofs — GameRuntime.Headless and the per-game projects (Economy.Headless, AlchemySim.Headless, Field.Headless, Briefing.Headless, CharacterBench) are complete sessions with scripted policies, used to verify behaviour without a renderer.
  • Godot — GameRuntime.Godot/GameFramework.cs drives RuntimeSession from the physics loop; GodotEventPort adapts the bus, ComponentNode wraps components, GameProfile reads a profile resource, GodotLogger reports faults. A Godot project (project.godot, Main.tscn) is included as the reference scene.

Testing

dotnet run --project src/GameRuntime/GameRuntime.Tests -c Release

Alongside the core session tests, each engine component has its own test project (GameRuntime.Calendar.Tests, .Economy.Tests, .Diplomacy.Tests, .Relationship.Tests, .Tutorial.Tests, .WorldEvents.Tests). They cover ordering, quiet/answered requests, checkpoints, replay divergence and source guards.
