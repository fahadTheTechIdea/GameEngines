## Algorithm and design

Combine terrain-aware weighted route search with region-local directional guidance and an explicit connection hierarchy. Cost terms can include travel length, slope, terrain class, avoidance and route reuse; hard exclusion, passage width and required interfaces are separate constraints. Support irregular and curved alignments, authored/grid alignments, branches and loops under one network contract. Tensor/contour guidance is a candidate for relevant surface layouts, not a universal requirement. Crossings declare levels and passage modes. Bridges, tunnels and portals are selected capabilities with valid endpoints and source requirements, never a silent escape from an impassable mask. Plan coarse regional connections between authored or suitability-derived destinations first, then settlement approaches, primary streets and district-local streets. Select a sparse candidate graph from purposeful travel demand; add loops only for declared redundancy/gameplay needs. Route each edge through the terrain and validate its full envelope. Administrative county/country borders are ownership constraints, never automatic road lattices. Settlement extents may be irregular, disjoint or grow along existing corridors. Derive urban blocks only from valid bounded street faces after the route network exists. Route/content feedback revises the owning plan within finite budgets; it must not fill the whole world with roads to create parcels.

### Proposed connection solver sequence

1. Resolve required origin/destination pairs and movement modes from gameplay/content intent. Add authored regional entry/exit ports; never infer destinations from every cell of a square partition.
2. For a supported surface domain, construct candidate links from required pairs plus a bounded proximity graph. Evaluate Delaunay or nearest-neighbor candidates as sparse search aids, not final roads. Disconnected candidates expand only within an explicit work budget; distance-only pruning cannot silently erase a required connection around a barrier.
3. Search each candidate using A* on the qualified terrain/navigation sampling graph, with nonnegative distance, slope, avoidance and route-reuse costs. Use an admissible distance lower bound when available, or Dijkstra when it is not. Include heading/turn state if the selected movement profile requires it. Hard exclusions and passage width are feasibility tests, not merely expensive cost terms.
4. Select a feasible backbone that serves required destinations, then add loops/alternative routes where the game requires redundancy or access. An MST is only a candidate backbone: directed reachability, bottlenecks, loops and protected source connections still need independent checks. Preserve graph connectivity while reusing compatible corridors and forming explicit junctions.
5. Within a settlement, grow local candidate streets from real primary streets, activity centers and required access fronts. Guide steps by region-local direction fields, terrain suitability and source demand. A grid direction field applies only inside its declared district; contour-following guidance must still reach destinations and respect grade/crossings. Stop when declared access/capacity is satisfied or the budget fails, not when the whole world has been covered with blocks.
6. Simplify or smooth qualified polylines within a declared geometric tolerance, then recheck full swept width, intersections, levels and source interfaces. Extract bounded urban faces only afterward; return unresolved capacity to the owning network/region plan with a finite retry limit.

These are proposed implementation choices to qualify, not a claim of code already present. Candidate-graph construction and sampling resolution are explicit parameters recorded in evidence. A path search failure on a coarse representation cannot be reported as proven physical impossibility without the declared resolution/refinement checks. Route rationale, rejected crossings and active costs are inspectable in S09.
