## Algorithm and design

Follow the canonical GameArts workflow from real approved source crops. Generate and approve isolated masters/frames as required, preserving camera, scale, style and source dimensions. Discover moving components and separate static bodies from animated components. Derive the tile inventory from actual map topology: borders, corners, transitions, junctions and allowed orientations. Use canonical deterministic atlas/bundle tools to pack measured assets, record masks/pivots/sockets and hashes. Do not ask image generation to fabricate a packed atlas or invent frame coordinates. Optional adjacency solving operates on approved compatible modules only; it cannot alter the approved map or waive asset coverage.


## Inputs and outputs

**Inputs:** Qualified full map, approved mockup crops, exact production inventory, art profile, component/animation requirements and canonical packing tools.

**Outputs:** Approved full asset set, tile transition set, separated moving parts, measured atlases, source/rights provenance and verified bindings for every required map instance.

## Failure handling and operations

Validate inputs and required capabilities before expensive work. Apply explicit cancellation and finite work/resource budgets at stage boundaries and inside iterative work. Return attributed unsatisfied constraints instead of silent fallback, missing required content or partial success. Preserve prior accepted output on failure. Use the existing Log/Audit/Notification owners for applicable generation, export and review boundaries; UI consumers display actionable failures and cancellation. Record source/input identities, stage outcome and unresolved dependencies. Retry only after the cause or inputs change, with the same declared reproducibility guarantees.

Recovery is a coherent correction of the current owner and affected inputs, followed by focused checks. Do not restore a retired implementation as a runtime fallback. Artifact approval gates apply only to the relevant visual stages and exact revisions.

## Verification and acceptance cases

- Validate every atlas rectangle is in bounds and every source/hash/approval reference resolves.
- Inspect tile seams, irregular route edges, terrain transitions and repeated scale at native resolution.
- Verify separated components align and animation frames preserve pivots and attachment points.
- Compare required versus produced inventory for the entire city; a sample sprite set cannot pass.

Run relevant checks with commands, environment, input/source digests and observed outcomes recorded. NOT RUN is not PASS. Existing tests are baseline evidence only. Keep implementation, local technical qualification, browser/native review, owner acceptance and unavailable CI/release gates distinct.

## Risks and boundaries

Tile shape and rendering style can constrain faithful rasterization. Resolve mismatches through reviewed assets/bindings rather than redesigning the map silently. Rights and provider rules apply to actual sources.
